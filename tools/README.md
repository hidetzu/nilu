# Development checks

How to build and check Nilu as it is now.

## What is needed

- The Zig version the [README](../README.md#build-from-source) names, pinned in
  `.mise.toml`. Run it through `mise exec --` when the `zig` on the path is another
  version, and confirm with `zig version`.
- Node.js, for the checking tools in this directory. They read files only.
- A native C compiler (`cc`) for the C host checks, which also run under `zig cc`.
- Lua 5.5 (`lua5.5`) only to capture reference answers again (see below), never
  for an ordinary build or check.

## The gates

```sh
zig build check --summary all        # the complete gate, before every pull request
zig build stage-check --summary all  # a faster gate while developing
zig build naming-check               # Zig names; run it after adding or renaming a file or declaration
zig build dist                       # the release build for the five targets, with SHA256SUMS
zig build --help                     # every entry point
```

`check` is what a pull request must pass. It runs:

| Step | What it checks |
|---|---|
| `fmt-check` | Zig formatting |
| `test` | the source tests: everything reachable from `src/root.zig` |
| `docs-check` | carried references, recorded digests and document links |
| `c-test` | the carried C cases (`test/c/`) against the library, under the native compiler and `zig cc` |
| `cli-test` | the carried command cases against the built `nilu` |
| `module-test` | the command's reader for `require`, `dofile` and `loadfile`, over files it writes |
| `manual-check` | every example block of both manuals, run and compared with its output |
| `example` | the C hosts in `examples/` and `test/install/stack.c`, built with `zig cc` against the installed header and library; each prints its `.out` |
| the `*-test` fixture suites | the checking tools themselves, against small fixtures |

`stage-check` runs formatting, the source tests, the reference checker, the naming
checker and the tooling fixtures; it does not replace `check`. `dist` is not part of
`check`: it builds every target, runs the host's own binary with `-v`, writes
`SHA256SUMS`, and says which target ran and which were only built. A target that
was only built has not been shown to work.

The workflow in `.github/workflows/check.yml` runs `check` on every push to `main`
and every pull request.

## Running a part

```sh
zig build test -Dtest-filter=parser        # the source tests whose name contains "parser"
node tools/list-tests.mjs --count          # the declared tests, counted without building
zig build docs-check -- --only=manual-contracts
zig build docs-check-test -- --list
```

`zig build test -Dpoison-registers=true` runs them with a VM that fills the registers it
regrows with a poison number instead of leaving what they held (ADR 0005): after a change to
the compiler, it shows a register read before it is written.

The test runner announces how many tests it ran. An empty selection, a skipped
test, a failed assertion or a leak under the testing allocator fails the step.
When a source file or a case is added, compare the runner's count with
`list-tests.mjs --count`: a declared test is not a test that ran, and a test in a
file that `src/root.zig` does not reach is never compiled.

When a check fails inside the test wrapper and its output is cut, run the test
binary the failure names (`failed command: … --name test`, under `.zig-cache/o/`)
directly to see all of it.

## Reference answers from Lua

The files `test/fixtures/lua55-*.txt` hold answers captured from `lua5.5` 5.5.1;
the source tests compare Nilu with them. They are never generated by Nilu. To
capture one again, run its script with the capture date and compare:

```sh
lua5.5 tools/capture-expressions.lua 2026-10-23 > /tmp/nilu-expressions.txt
cmp /tmp/nilu-expressions.txt test/fixtures/lua55-expressions.txt
```

There is a `tools/capture-*.lua` for each fixture except `lua55-numerals.txt`, whose
numeral answers were carried as captured. A fixture changes only when Lua's answer
is captured again; it is never edited to fit Nilu.

## Looking at compiled code

`compiler.write(writer, prototype)` prints a prototype's constants and instructions
without running them. To see what a source compiles to, call it from a scratch
test (`zig build test -Dtest-filter=<that test>`) and remove the test afterwards.
A listing shows what was compiled; it is not evidence of what running it does.

## Code layout

Where the code lands moves how fast a script runs as much as a change to it
does: in a build that left placement to the linker, an edit to the compiler
alone, which a script's loops never run, has moved some scripts by several
percent. So every build, a release included, places the code that
runs a script itself:

- The VM's instruction arms have a section of their own on every target
  (`src/vm.zig`), starting on a page, so that a change elsewhere does not move
  them; within it they keep the compiler's order. Each arm is aligned to
  `-Darm-slot` bytes.
- On ELF targets a linker script (`build.zig`) places the rest of the running
  code too: the VM, the runtime, the library and the standard library's hash and
  allocator, in name order by groups, from a 4096-byte boundary plus
  `-Darm-shift`. Each later group starts on a 4096-byte boundary plus
  `-Dgroup-gap` bytes (`-Dgroup-page`), so that one group's size does not move
  the others within a page: code that differed only in where it sat moved some
  scripts by over 10%. The Mach-O and COFF linkers take no script, so there only
  the arms are placed.
- Code that runs once per function loaded (preparing a prototype) is marked
  cold, which keeps it out of the groups, and the library's entry functions are
  named by the library function, not numbered, so a change elsewhere does not
  reorder them.

The defaults are the layout that measured best in ReleaseSafe among sixteen
; `zig build --help` names them. A measurement changes them to tell a
change from where the code landed. A change that resizes much of the running
code, as leaving out the frame pointer did, calls for choosing them again.

## Measuring speed

`tools/speed.mjs` runs the scripts in `bench/` under `perf stat -e cycles:u` and
compares builds; it needs Linux, `perf`, `setarch` and `taskset`. Every build must
print what the first one prints, and Lua 5.5 can be one of them (`lua=lua5.5`).

A change to the running code itself still moves what comes after it, so compare
in several layouts, not in one:

```sh
# four layouts of the code before the change (in a worktree of the base
# revision); then the same four of the changed tree, as tmp/speed/after-*
for l in 64,0,0 16,1024,192 128,2048,448 32,3072,704; do   # slot,shift,gap
  IFS=, read slot shift gap <<< "$l"
  zig build -Doptimize=ReleaseFast -Darm-slot=$slot -Darm-shift=$shift -Dgroup-gap=$gap --prefix tmp/speed/before-$slot
done
node tools/speed.mjs --runs=8 \
  before=tmp/speed/before-64,tmp/speed/before-16,tmp/speed/before-128,tmp/speed/before-32 \
  after=tmp/speed/after-64,tmp/speed/after-16,tmp/speed/after-128,tmp/speed/after-32
node tools/speed.mjs --list                        # the scripts
node tools/speed.mjs --only=fib,method a=<dir> b=<dir>
```

A shift alone moves the whole section and keeps its functions where they are
against each other, and that relative placement has moved a script by several
percent while the code that ran was the same; so the four layouts
above change the shift, the slot and the gap together.

Where the data lands matters as well: the environment's size moves the stack,
and with it which stores and loads the processor takes for colliding (their low
twelve address bits agree). So the runner gives each program only `PATH` and a
padding variable, padded by another amount on each pass and by the same amount
for every build in that pass; `--pad=<bytes>` fixes it while looking into one
case. A count of store-forwarding stalls (`ls_bad_status2.stli_other` on this
processor) measured by hand without that is not evidence about the code.

The runner interleaves the runs and reports, for each script, each set's median
and the ratio to the first set: the median of the per-layout ratios and their
range. `mixed` says the layouts disagree about which is faster; such a difference
belongs to the layout, not to the change. Measure the same builds as both sets
first: what they differ by is the machine's noise for each script, which a
difference must exceed, and which is wider for a script that allocates much.
Code inside the pinned section still moves when the change is there, which is
what the several layouts are for. Another program busy on the same core or its
sibling moves the numbers as well, more than any of this: check the load the
runner prints, and measure again when two runs of the same builds disagree.

The measurements, what was tried and what was dropped are in the development
record, which is not part of this repository.
